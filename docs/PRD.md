## 2. 项目背景

普通植物爱好者在养护过程中经常遇到三个问题：不知道植物是什么、不知道异常症状是什么、不知道何时以及如何养护。相关信息散落在搜索引擎、短视频和社交平台中，内容质量不稳定，也难以与用户自己的植物建立长期联系。

AI 园林助手希望提供一个轻量、连贯的使用流程：用户识别植物或描述问题，获得结构化建议，再把植物加入个人花园并持续记录养护活动。

项目已将两版早期实现融合为 Taro 本地 MVP。此前形成的 48 小时和七天 Sprint 文档只保留有效功能方向，不作为当前进度、人员分工或交付期限依据。

## 3. 产品定位

### 3.1 产品定义

AI 园林助手是一款面向普通植物爱好者和植物养护新手的免费微信小程序，提供植物识别、病虫害诊断、植物档案管理和养护提醒能力。

### 3.2 目标用户

- 刚开始养植物、缺少系统养护知识的新手。
- 在家庭、宿舍或办公室养少量植物的普通用户。
- 希望快速记录浇水、施肥等行为的植物爱好者。

首版不专门覆盖专业园林从业者、农业生产者、大型园区管理者和科研人员。

### 3.3 核心价值

- 降低植物识别和问题判断的门槛。
- 将一次性查询转化为可持续的个人植物管理。
- 用明确、可执行的养护建议替代零散信息。
- 通过提醒减少忘记浇水、施肥等常见问题。

### 3.4 产品原则

- 先可用，再扩展：首版优先完成核心流程，不追求复杂平台能力。
- 建议可执行：结果应说明用户下一步可以做什么。
- 表达有边界：诊断结论使用“可能”“疑似”等措辞，不冒充专业检测。
- 服务可替换：识别和大模型服务通过统一接口接入，不在需求阶段锁定厂商。
- 免费使用：首版不设置付费、会员、广告或次数购买。

## 4. 产品目标与非目标

### 4.1 首版目标

1. 用户可以通过图片获得植物识别结果。
2. 用户可以通过图片和文字描述获得植物问题诊断建议。
3. 用户可以将识别结果或手动录入的植物加入个人花园。
4. 用户可以记录主要养护行为并查看最近状态。
5. 用户可以创建本地养护任务；完成微信平台和服务端配置后，可通过微信订阅消息接收通知。
6. 在外部 AI API 尚未确定时，产品仍可以通过可替换的模拟服务完成演示和流程验证。

### 4.3 首版非目标

- 不建设植物商城、交易或支付能力。
- 不建设社区、动态、评论、私信或专家问答。
- 不建设面向运营人员的独立内容管理后台。
- 不提供专业农业生产、园林工程或批量设备管理功能。
- 不承诺识别和诊断结果可替代植物病理检测或专业人员意见。
- 不开发原生 iOS、Android App 或其他小程序平台版本。

## 5. 产品结构

首版包含五个一级功能模块：

| 模块 | 主要职责 |
| --- | --- |
| 首页 | 提供搜索、核心功能入口、养护提示和植物推荐 |
| 植物识别 | 上传或拍摄图片，展示植物资料和养护建议 |
| 病虫害诊断 | 接收图片和文字描述，展示可能问题及处理方案 |
| 我的花园 | 管理个人植物、养护记录、任务和提醒 |
| 个人中心 | 展示用户信息、使用记录和基础设置 |

建议采用底部导航承载“首页、识别、花园、诊断、我的”。最终导航数量和交互可在 UI 设计阶段根据微信小程序规范调整，但不得隐藏核心入口。

## 6. 关键用户流程

### 6.1 识别植物并加入花园

1. 用户从首页或识别页进入植物识别。
2. 用户拍照或从相册选择一张植物图片。
3. 系统检查图片格式和大小，然后提交识别。
4. 系统展示候选植物、置信度、植物资料和养护建议。
5. 用户选择正确结果并加入“我的花园”。
6. 用户补充植物昵称、位置和获得日期；提醒设置在微信订阅消息完成后启用。
7. 系统生成个人植物档案。

### 6.2 诊断植物问题

1. 用户进入病虫害诊断页。
2. 用户上传图片、输入文字描述，或同时提供两者。
3. 用户可补充症状持续时间、最近浇水和光照等信息。
4. 系统返回可能问题、判断依据、严重程度和处理建议。
5. 用户可保存本次诊断，并关联至花园中的某一株植物。
6. 用户可根据建议创建后续观察或养护提醒（产品要求，当前尚未实现从诊断结果直接创建）。

### 6.3 日常养护与提醒

1. 用户进入“我的花园”，选择一株植物。
2. 用户记录浇水、施肥、修剪、换盆或其他行为。
3. 系统更新该植物的最近养护状态。
4. 用户创建下一次养护任务。
5. 用户主动授权微信订阅消息（待实现）。
6. 到达计划时间后，系统发送订阅提醒，用户进入小程序完成任务（待后端与微信平台能力完成后验收）。

## 7. 功能需求

### 7.1 首页

#### 7.1.1 搜索

- 支持按植物中文名、常见别名搜索植物资料。
- 输入为空时不发起搜索。
- 无匹配结果时展示空状态，并引导用户尝试拍照识别。
- 在尚无完整植物数据库时，可先使用有限的本地或服务端示例数据验证流程。

#### 7.1.2 核心入口

- 提供植物识别、病虫害诊断和我的花园的明显入口。
- 点击入口必须进入对应实际功能页面，不使用不可操作的占位卡片。

#### 7.1.3 每日养护提示

- 每次进入首页展示一条简短、明确的植物养护提示。
- 提示内容首版可来自内置内容，不依赖运营后台。
- 内容应避免绝对化和有安全风险的用药建议。

#### 7.1.4 热门植物

- 展示常见家庭植物及缩略图。
- 点击后进入植物详情。
- 首版推荐内容可以固定配置，不要求个性化推荐算法。

当前进度：推荐卡片已展示，但点击进入详情尚未实现。

### 7.2 植物识别

#### 7.2.1 图片输入

- 支持微信拍照和相册选择。
- 首版每次识别至少支持一张图片。
- 上传前显示图片预览，允许删除并重新选择。
- 图片不符合格式、大小或读取失败时，提供明确提示。
- 用户提交前应看到图片用途说明。

#### 7.2.2 识别过程

- 提交后展示稳定的加载状态，防止重复提交。
- 请求失败时说明原因，并允许用户重试。
- AI 服务尚未接入期间，使用统一模拟接口返回固定格式数据。
- 后续接入真实服务时，不改变页面与业务层使用的数据结构。

#### 7.2.3 识别结果

结果至少包含：

- 最可能的植物名称和常见别名。
- 识别置信度或“高、中、低”可信等级。
- 一至两个候选结果，供低置信度场景选择。
- 植物简介。
- 光照、浇水、温度、湿度、土壤和施肥建议。
- 对宠物或儿童的潜在毒性提示；数据未知时明确标注未知。
- “加入花园”和“重新识别”操作。

识别失败或置信度过低时，不得强行给出唯一确定结论，应提示用户补拍叶片、花朵或植株全貌。

当前进度：页面已支持候选选择交互，但默认 Mock 候选为空；`PlantCareGuide` 尚无湿度字段，因此候选流程和湿度建议都未达到验收条件。

#### 7.2.4 识别历史

- 保存识别时间、图片缩略图、最终选定植物和识别结果摘要。
- 用户可以查看和删除单条记录。
- 未登录状态下可使用本地存储；未来登录后是否云同步由后续版本决定。

当前进度：本地保存、查看和删除已实现，但历史在初始结果返回时立即写入，用户随后改选候选时不会同步更新，尚不满足“最终选定植物”的要求。

### 7.3 病虫害诊断

#### 7.3.1 诊断输入

- 支持仅上传图片、仅输入文字描述，以及图片与文字组合输入。
- 文字描述不能为空白字符，且应设置合理长度限制。
- 图片输入要求与植物识别一致。
- 可选补充信息包括植物名称、症状持续时间、最近浇水、光照环境和近期用药。

#### 7.3.2 诊断结果

结果至少包含：

- 一个或多个可能的问题名称。
- 可信等级和判断依据。
- 可观察到的典型症状。
- 可能原因。
- 建议立即采取的操作。
- 后续养护或观察步骤。
- 必要的隔离、用药和人宠安全提醒。
- 需要进一步补拍或咨询专业人员的条件。

诊断结果必须附带提示：结果由自动化系统辅助生成，仅供养护参考，不能替代专业检测。

当前进度：结构化 Mock 结果和边界提示已实现；根据诊断建议直接创建后续任务或提醒尚未实现。

#### 7.3.3 诊断历史

- 用户可保存、查看和删除诊断记录。
- 记录可选择关联到个人花园中的植物。
- 历史记录至少保存诊断时间、输入摘要、结果摘要和处理建议。

### 7.4 我的花园

#### 7.4.1 植物档案

- 支持从识别结果加入植物。
- 支持不经过识别、手动创建植物档案。
- 支持编辑和删除个人植物。
- 植物档案至少包含名称、昵称、封面图、摆放位置、获得日期、备注和创建时间。
- 删除前必须二次确认；删除后同时处理其关联任务和记录，具体策略在技术设计中确定并对用户说明。

#### 7.4.2 花园列表

- 展示植物封面、昵称、名称、最近浇水时间和待办状态。
- 支持进入植物详情。
- 没有植物时展示空状态，并引导用户识别或手动添加。

#### 7.4.3 养护记录

- 支持记录浇水、施肥、修剪、换盆、喷药和自定义事项。
- 记录至少包含类型、时间和备注。
- 用户可查看单株植物的时间线。
- 首版至少支持删除误操作记录；是否允许编辑由交互设计阶段确定。

#### 7.4.4 养护任务

- 支持创建一次性或按固定周期重复的养护任务。
- 任务至少包含关联植物、任务类型、计划时间、重复规则和备注。
- 用户可以将任务标记为完成、跳过或延后。
- 完成浇水等任务时，可同时生成对应养护记录。
- 首页或花园页应展示当天待办和逾期任务。

#### 7.4.5 微信订阅消息

- 只有用户主动触发并授权后，才能发送订阅消息。
- 授权拒绝或发送失败时，不阻断本地任务创建。
- 提醒消息点击后应进入对应植物或任务页面。
- 具体模板、发送频率、服务端调度和微信平台规则在技术设计阶段确认。
- 产品不能承诺永久或无限次提醒，应在界面中如实说明微信订阅授权限制。

当前进度：本地任务可用，但订阅消息整体未开始实现。

### 7.5 个人中心

#### 7.5.1 用户状态

- 首版允许用户不登录即可体验主要功能。
- 用户信息能力以微信平台允许的授权范围为准。
- 登录与云端同步不是首版可用闭环的前置条件。

#### 7.5.2 数据概览

- 展示花园植物数量、累计养护次数、识别次数和诊断次数。
- 统计值必须来自实际记录，不展示不可验证的模拟增长数据。

#### 7.5.3 历史与设置入口

- 提供识别历史、诊断历史、消息提醒设置、隐私说明和关于项目入口。
- 暂不提供会员、订单、积分和广告设置。

当前进度：历史、隐私说明和关于项目入口可用；“云服务与提醒”入口仅展示尚未开通的说明，不是可配置的消息提醒设置。

## 8. 数据与状态要求

### 8.1 首版数据策略

首版以功能可用为目标。在正式后端未建设完成时，个人植物、养护记录、任务、识别历史和诊断历史先保存在本地。模拟识别与诊断服务必须与未来真实 API 使用相同的业务数据结构。仓库中的 Express 服务是本地 Mock 接口和未来适配骨架，不等同于已部署的数据后端。

微信订阅消息通常需要服务端保存任务并定时调用微信接口。该能力不能仅依赖小程序本地运行，因此进入订阅消息开发前必须补充最小后端和微信服务端方案。

### 8.2 核心数据对象

| 数据对象 | 主要信息 |
| --- | --- |
| 植物资料 | 名称、别名、简介、图片、养护建议、安全信息 |
| 用户植物 | 资料引用、昵称、位置、获得日期、封面、备注 |
| 养护记录 | 植物、类型、发生时间、备注 |
| 养护任务 | 植物、类型、计划时间、重复规则、状态 |
| 识别记录 | 图片、候选结果、可信等级、用户选择、时间 |
| 诊断记录 | 图片、文字描述、可能问题、建议、关联植物、时间 |

本地 MVP 的核心字段已在 `src/types/index.ts` 中落地。启用云端后，再补充服务端字段、索引、账号归属和数据迁移设计。

## 9. 异常与边界场景

- 用户未授权相册或相机时，说明原因并提供重新授权路径。
- 网络不可用时保留用户尚未提交的文字输入，避免无故丢失。
- 请求超时或服务繁忙时允许重试，但不得无限自动重试。
- 图片识别失败时提供补拍建议，而非只显示“失败”。
- 本地存储空间不足时提示用户，并避免破坏现有记录。
- 同一任务被重复点击完成时，只生成一条有效养护记录。
- 用户删除关联植物时，必须明确关联记录和任务将如何处理。
- AI 返回缺失或不符合格式的数据时，页面应降级显示可用部分，并记录错误供排查。

当前进度：图片校验、请求体限制、限流和基础请求失败提示已实现；权限拒绝恢复、输入保留、超时分类、结构化降级和完整重试状态仍需逐项实现和测试。

## 10. 非功能需求

### 10.1 易用性

- 核心操作适配单手使用，主要按钮文字清晰。
- 所有请求提供加载、成功、失败和空状态。
- 不使用专业术语堆砌；必要术语提供通俗解释。
- 重要操作结果通过页面状态或提示明确反馈。

### 10.2 性能

- 首屏应优先展示框架和可用入口，非关键图片延迟加载。
- 上传前应在不明显影响诊断质量的前提下压缩大图。
- 列表数据采用分页或合理数量限制，避免一次加载全部历史图片。
- 具体性能阈值在完成技术选型和首个原型后确定。

### 10.3 隐私与安全

- 上传前明确说明图片将用于识别或诊断。
- 只申请完成当前操作所需的微信权限。
- 不采集与功能无关的联系人、位置或设备信息。
- 在接入第三方 AI 服务前，明确其数据处理和保存政策。
- 提供隐私说明和本地数据清除入口。
- 图片保存期限、服务端删除机制和第三方数据传输规则须在真实 API 上线前确定。

### 10.4 兼容性

- 主要保证当前主流微信版本中的小程序体验。
- H5 可作为技术框架兼容方向，但不作为首版独立发布目标。
- 不要求首版支持原生 App 和其他小程序平台。

## 11. 内容与提示规范

- 不把低置信度结果表述为确定事实。
- 农药、杀虫剂和肥料建议必须包含按产品说明使用及人宠安全提示。
- 对疑似严重传染性问题，优先建议隔离植株并进一步确认。
- 对数据库未知的信息显示“暂无可靠信息”，不得自动编造。
- 每日提示和热门植物首版由项目内配置维护，不建设内容运营后台。

“内容运营后台”是供工作人员在不修改代码的情况下维护植物知识、首页推荐、每日提示和纠错内容的管理网站。本项目不建设该后台，相关内容直接通过代码配置或项目内数据文件维护。

## 12. MVP 验收标准

满足以下条件时，可认为首版核心产品流程达到可验收状态。当前代码只完成其中一部分，实际结果以第 4.2 节进度表为准：

1. 用户能够完成图片选择、识别提交、结果查看和加入花园的完整流程。
2. 用户能够使用图片、文字或两者组合提交诊断并查看结构化建议。
3. 用户能够手动添加、编辑和删除植物档案。
4. 用户能够新增至少五类养护记录，并在植物时间线中查看。
5. 用户能够创建、完成、跳过和延后养护任务。
6. 在完成微信服务端配置后，授权用户能够收到至少一种养护订阅提醒。
7. 识别历史和诊断历史可以保存、查看和删除。
8. 关键页面均具备加载、空、失败和重试状态。
9. 在未接入真实 AI 服务时，模拟服务可以稳定演示同样的业务流程。
10. 用户可以查看隐私说明并清除本地个人数据。

## 13. 后续迭代候选

以下需求不进入首版承诺，仅作为未来候选：

- 接入经评估的植物识别服务和大模型诊断能力。
- 登录后的多设备数据同步与备份。
- 基于植物品种、季节和环境的动态养护计划。
- 天气或位置相关提醒；启用前需单独评估定位权限和隐私影响。
- 连续照片对比和生长相册。
- 更完整且具备可靠来源和授权记录的植物知识库。
- 用户反馈纠错和识别结果质量评估。

## 14. 待后续确认事项

以下事项不阻塞当前本地 MVP，但会影响微信正式版本：

- 首版植物知识数据的来源、授权方式和覆盖范围。
- 百度植物识别和百度云上 DeepSeek 候选服务的准确产品名称、官方文档、接口、鉴权和模型 ID，以及最终 AI 选型的准确率、成本、响应时间、隐私和可用性要求。
- CloudBase 或其他后端方案、微信订阅消息模板与任务调度方式。
- 本地数据升级到云端时的账号体系和迁移策略。
- 已申请的正式 AppID 下，认证、名称、备案备注、隐私配置、成员权限、开发者工具和真机兼容性结果。

## 15. 需求变更规则

- 新需求先判断是否直接支持“识别、诊断、管理、提醒”核心闭环。
- 会引入支付、社区、专业生产管理或复杂后台的需求默认进入后续版本评估。
- 涉及第三方 AI、微信权限或用户数据上传的功能，开发前必须补充技术与隐私说明。
- 需求确认、设计、开发和验收按正常项目节奏推进，不再以 48 小时极限开发为目标。
